# Decisions

[[ASTRA|← Home]]

A log of significant technical and architectural decisions, including the reasoning behind them.

---

## 2026-06-13 — Ollama URL and model name are hardcoded

**Decision:** `BASE_URL` in `ollama_client/async_client.rs` and the model name in `req_handler.rs` are intentionally hardcoded constants, not config values.

**Reasoning:** The project is in early development. Extracting these to environment variables or a config file adds complexity before there is a real need. When multi-environment support or model switching becomes a requirement, this will be revisited.

---

## 2026-06-13 — Tool implementations use shell commands via `std::process::Command`

**Decision:** Tools invoke shell scripts or system commands directly rather than using Rust libraries.

**Reasoning:** Keeps the integration layer simple and language-agnostic. Shell scripts are easy to write and test independently. If a tool grows complex enough to warrant a native Rust implementation, it can be migrated at that point.

---

## 2026-06-13 — WebSocket as the primary transport layer

**Decision:** All client-server communication will be built on WebSocket from the start, including the text interface.

**Reasoning:** Voice is a core target feature. Migrating from HTTP/SSE to WebSocket once a web client is already built against it is a costly refactor touching both ends. Starting with WebSocket for text means voice can be added as a new message type over the same connection without changing the transport layer. The upfront complexity cost is lower than the future refactor cost.

---

## 2026-06-20 — Sliding window size derived from context window minus system prompt

**Decision:** The sliding window size N is not a hardcoded constant. It is computed at startup as `max_context_tokens - system_prompt_tokens - response_buffer`. The system prompt is always guaranteed to fit; conversation history fills whatever space remains.

**Reasoning:** The system prompt (persona, rules, behavioral config) is the stable, fundamental context — it must always be present. Conversation history is the variable part. By deriving N from actual config size, the window shrinks automatically when config grows, and no manual tuning is needed. Token counting will use a character-count heuristic (`chars / 4`) initially; a proper tokenizer can replace it later if accuracy becomes a problem. Ollama's `prompt_eval_count` in API responses can be used to validate the estimate over time.

---

## 2026-06-20 — WebSocket message schema: wrapped envelope with client-generated request_id

**Decision:** All WebSocket messages use a wrapped envelope: `{ "type": "...", "request_id": "...", "payload": { ... } }`. The `request_id` is generated by the client and echoed on all server messages associated with that request. It is optional on server-initiated messages with no associated request. Error codes are deferred until the full error surface is known.

**Reasoning:** Wrapped structure deserializes cleanly in Rust — a generic envelope with a typed payload maps directly to a tagged enum via serde. Client-generated `request_id` allows correlation before the first response chunk arrives; server-generated would leave the client unable to correlate early messages. `done: true` on `text_chunk` signals response completion for that `request_id` while keeping the connection open.

---

## 2026-06-20 — Streaming response routing: peek first chunk, branch on content vs tool_calls

**Decision:** When Ollama streams a response, Astra inspects the first substantive chunk to determine routing. If the `message` object contains a `content` field, forward chunks to the WebSocket client as they arrive. If it contains a `tool_calls` field, switch to buffer mode — accumulate the full response, dispatch the tool, re-enter the chat loop, then stream the follow-up text response.

**Reasoning:** The model commits to text or tool call early in generation — typically the first chunk signals which path it's on. Ollama's streaming format makes this detectable without deep buffering: `content` and `tool_calls` are mutually exclusive fields on the `message` object. Peeking at the first chunk keeps latency low for the common text path while correctly handling tool calls. Buffering the entire response before forwarding anything (simpler logic, more latency) was considered but rejected in favour of early detection.

---

## 2026-06-20 — Astra owns all conversation state

**Decision:** Astra is responsible for maintaining the `messages` array for each active conversation. Ollama receives no state between requests — the full history must be reconstructed and sent on every call.

**Reasoning:** Ollama's `/api/chat` is completely stateless. Continuity of conversation is an illusion created by replaying history. This makes conversation state a first-class architectural concern in Astra, not an afterthought. Starting with in-memory storage per session; persistence (disk or SQLite) deferred until multi-session or restart-survival is needed.

---

## 2026-06-20 — Hybrid two-layer config system: core and user

**Decision:** Config is split into two layers loaded from `config/core/` and `config/user/`. Core files define hard behavioral constraints (identity, tool rules, immutable behavior). User files define stylistic preferences (persona, name, collaboration style, coding preferences). Core is loaded first, user config appended after. User files can be absent or empty without error.

**Reasoning:** Some config must be stable and not overridable (fundamental behavior, tool safety). Other config is legitimately user preference (personality, tone, name). Separating them makes the distinction explicit and keeps core rules in developer control. Precedence is enforced by load order and phrasing — core uses hard constraint language ("always", "never"), user config uses softer preference language. This is not mechanically enforced but is sufficient for a single-user home server.

**Deferred:** Multi-user support, per-session config overrides, and validation of user config files are out of scope until needed.

---

## 2026-06-20 — Behavioral config lives in Astra, runtime tuning in Ollama Modelfile

**Decision:** System prompt and behavioral rules (persona, capabilities, tone) are owned by Astra and injected into every request. Hardware/runtime tuning (`num_ctx`, GPU layers, thread count) belongs in an Ollama Modelfile on the host machine.

**Reasoning:** Behavioral config should be version-controlled alongside the code that uses it and changeable without touching the Ollama machine. Runtime tuning is machine-specific and not meaningful to track in the Astra repo. System prompt size is also a per-token tax on every request, so config files should be kept concise.

---

## 2026-06-13 — Axum with shared `AppState` for tool registry

**Decision:** Tools are registered at startup into `AppState`, which is cloned into every request via Axum's `State` extractor.

**Reasoning:** Tools don't change at runtime, so a shared immutable list owned by `AppState` is the right fit. Avoids global state and keeps everything within Axum's ownership model.
