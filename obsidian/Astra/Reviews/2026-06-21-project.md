# Code Review — project — 2026-06-21

[[REVIEWS|← Reviews]]

## Summary

Phase 1 is functional but carries significant dead weight from the retired HTTP handler layer, and the tool implementation layer has a real async correctness bug that will cause problems under load. The most critical issue is synchronous `std::process::Command` being called inside async functions — this blocks the Tokio runtime thread. 16 total findings: 2 critical, 8 warnings, 6 suggestions.

## Findings

### Critical

**Finding C1**
- **File**: `src/tools/implementations.rs` lines 4–9, 11–14
- **Issue**: Both `echo_hello_world` and `list_contents` are `async fn` but call `std::process::Command::new(...).status()`, which is a **synchronous blocking operation**.
- **Why**: Tokio (the async runtime) schedules many tasks on a small pool of OS threads. When one task calls a blocking function, it occupies that thread entirely — no other tasks can run on it until the blocking call returns. If the shell script takes even a few hundred milliseconds, the whole server stalls. This is one of the most common async correctness bugs in Rust. The fix is to use `tokio::process::Command`, which is the async-aware version that runs the subprocess without blocking the runtime thread.
- **Direction**: Replace `use std::process::Command` with `use tokio::process::Command`. Change `.status()?` to `.status().await?`. Add `tokio` as a dependency with `process` feature enabled (it may already be available via `axum`).

---

**Finding C2**
- **File**: `src/tools/implementations.rs` line 6
- **Issue**: The shell script path is hardcoded as an absolute macOS home directory path: `/Users/anishkurani/Documents/Coding-Stuff/astra/src/integrations/script/echo.sh`.
- **Why**: This path only exists on one specific machine. The server fails silently or panics on any other host (a different developer machine, a home server, a Docker container). Paths like this also leak personal information. Script paths should be relative to the project root or configurable at startup.
- **Direction**: Use a path relative to the binary's working directory (e.g. `src/integrations/script/echo.sh`) or resolve against an env var or config value at startup. Relative paths work as long as the server is always started from the project root, which is true during development.

### Warnings

**Finding W1**
- **File**: `src/handlers/req_handler.rs` — entire file
- **Issue**: The file contains a large amount of dead code: `AppError`, `GenerateRequest`, `GenRequest`, `call_model()`, and `generate_model()` are all unreachable (routes were removed). `chat_model()` is commented out entirely. The only live types are `OllamaMessage` and `ChatRequest`.
- **Why**: Dead code creates noise that misleads future readers about what the system actually does. Rust's compiler will also emit `dead_code` warnings for these, cluttering build output and making it harder to notice real warnings. The live types (`OllamaMessage`, `ChatRequest`) belong in `ollama_client` anyway — they describe what Ollama's API expects, not what HTTP handlers need.
- **Direction**: Delete `AppError`, `GenerateRequest`, `GenRequest`, `call_model`, `generate_model`, and the commented-out `chat_model`. Move `OllamaMessage` and `ChatRequest` into `src/ollama_client/`. This is the Phase 2 refactor already in the backlog.

---

**Finding W2**
- **File**: `src/ollama_client/async_client.rs` lines 1–3
- **Issue**: `async_client` imports `ChatRequest` and `GenRequest` from `crate::handlers::req_handler`. The data flow is inverted — the HTTP client layer depends on the handler layer.
- **Why**: In a well-layered architecture, handlers depend on the client (they call it), not the other way around. When the client imports from handlers, you can't use or test the client without also loading the handler module. This will also become a compile problem once `req_handler.rs` is cleaned up, since the types will move. The request types describe the shape of Ollama's API — they belong in `ollama_client`, not `handlers`.
- **Direction**: Move `ChatRequest` and `GenRequest` (once cleaned up) into `src/ollama_client/` or a `src/types.rs` file. Update imports accordingly.

---

**Finding W3**
- **File**: `src/main.rs` lines 27–28
- **Issue**: Two `unwrap()` calls: `TcpListener::bind(...).await.unwrap()` and `axum::serve(...).await.unwrap()`.
- **Why**: `unwrap()` panics with a generic thread-panic message on failure. In `main()`, panics are technically acceptable since there's nowhere to propagate to, but `expect("reason")` is strictly better — it tells you *why* it failed in the panic message. Even better: propagate the error by making `main` return `Result<(), Box<dyn std::error::Error>>` and using `?`, which gives a clean error message without a panic trace.
- **Direction**: Either change to `.expect("could not bind to port 3000")` / `.expect("server error")`, or change `main`'s return type to `Result<(), Box<dyn std::error::Error>>` and use `?`.

---

**Finding W4**
- **File**: `src/tools/registry.rs` line 53
- **Issue**: `serde_json::to_value(NoArgs::new()).unwrap()` — an `unwrap()` in production startup code.
- **Why**: `serde_json::to_value` returns `Result` because serialization can fail in theory. In this case it won't — you're serializing a known struct — but `unwrap()` anywhere in production code is a yellow flag. It also sets a pattern: the next developer adds a more complex parameter struct and copies the same `unwrap()`, and now failure is a real risk. Use `expect()` with context at minimum.
- **Direction**: Change to `.expect("NoArgs serialization is infallible")` to document the intent. Or pre-define the parameter JSON as a `serde_json::json!({...})` literal and skip `NoArgs` entirely.

---

**Finding W5**
- **File**: `src/handlers/ws_handler.rs` line 5
- **Issue**: `handle_socket` is declared `pub` but is only ever called from `ws_handler` in the same file. Nothing outside the module needs to call it directly.
- **Why**: Rust's visibility system is about clearly communicating what is part of a module's public API. Marking something `pub` when it's an internal implementation detail invites callers to depend on it, making future refactoring harder. `pub(crate)` (accessible anywhere in the crate) or no modifier at all (private to the module) would be correct here.
- **Direction**: Remove `pub` from `handle_socket` to make it private to the module.

---

**Finding W6**
- **File**: `src/main.rs` lines 1–4
- **Issue**: Three unused imports: `use axum::extract::ws::WebSocket`, `use axum::extract::{State, WebSocketUpgrade}`, `use axum::response::Response`. None of these are used in `main.rs` — they are all used inside `ws_handler.rs`.
- **Why**: Unused imports are noise. Rust warns about them with `dead_code` / `unused_imports` lints. They also imply false ownership — a reader of `main.rs` might think the main module is doing WebSocket work directly.
- **Direction**: Delete these three import lines from `main.rs`.

---

**Finding W7**
- **File**: `src/handlers/ws_handler.rs` lines 93–94
- **Issue**: JSON parse errors from incoming WebSocket frames are silently discarded with `Err(_) => {}`. The client receives no feedback when it sends a malformed message.
- **Why**: Silent error discard makes debugging extremely hard — if a client sends a slightly wrong message format, it gets no response and no indication of what went wrong. The server also has no record of the failure. At minimum, an `Error` envelope should be sent back to the client so it can surface the problem.
- **Direction**: On parse error, construct and send an `Envelope` with `Message::Error(ErrorPayload { message: "invalid message format".into(), code: "PARSE_ERROR".into() })` back over the socket before continuing.

---

**Finding W8**
- **File**: `src/integrations.rs`
- **Issue**: `pub mod script` declares a Rust module, but `src/integrations/script/` only contains shell scripts (`.sh` files), not Rust source files. There is no `script.rs` or `script/mod.rs` to back this declaration.
- **Why**: If Rust finds `pub mod script` but no corresponding `.rs` file, it will fail to compile. If this currently compiles, there must be an empty `mod.rs` somewhere — either way the module is dead (no Rust code in it). This module declaration should be removed, and shell scripts don't need a Rust module wrapper at all.
- **Direction**: Delete `src/integrations.rs` and the `mod integrations;` line in `main.rs` (if present). Shell script files are just files on disk — they don't need to be declared as Rust modules.

### Suggestions

**Finding S1**
- **File**: `src/tools/implementations.rs` lines 1–2
- **Issue**: Both `use std::process::Command` and `use std::process::ExitStatus` are imported separately when they come from the same path.
- **Why**: Minor style issue. They can be merged as `use std::process::{Command, ExitStatus}`. This is the idiomatic Rust convention for grouping imports from the same module.
- **Direction**: Merge into a single `use` statement with braces.

---

**Finding S2**
- **File**: `src/state.rs`
- **Issue**: `AppState::new()` takes no arguments and creates a default state. In Rust, this pattern should implement `std::default::Default` so that `AppState::default()` works.
- **Why**: `Default` is a standard trait that signals "this type has a sensible zero/empty/startup value." Many Rust frameworks and test harnesses use `Default::default()` to construct types in generic contexts. Not implementing it means `AppState` can't be used in those contexts without ceremony. The implementation is trivial — `Default` can delegate directly to `new()`.
- **Direction**: Add `impl Default for AppState { fn default() -> Self { Self::new() } }`.

---

**Finding S3**
- **File**: `src/handlers/req_handler.rs` line 46
- **Issue**: `OllamaMessage.role` is `String`, which allows any value. In practice only four values are valid: `"system"`, `"user"`, `"assistant"`, `"tool"`.
- **Why**: Using a free-form `String` for a field with a fixed set of valid values means typos (e.g. `"assistent"`) are only caught at runtime when Ollama rejects the request. An enum encodes the constraint at the type level — the compiler will reject invalid values before the code even runs. This also makes `match` expressions on role exhaustive and compiler-checked.
- **Direction**: Define `pub enum Role { System, User, Assistant, Tool }` with `#[serde(rename_all = "lowercase")]`. Replace `role: String` with `role: Role` in `OllamaMessage`. Update all construction sites.

---

**Finding S4**
- **File**: `src/tools/registry.rs` lines 32–46
- **Issue**: `NoArgs` is a `pub` struct used only inside `register_tools()`. It exists to serialize an empty parameter object but could be replaced with a `serde_json::json!({ "type": "object", "properties": {} })` literal inline.
- **Why**: The struct adds indirection for a one-off use. Keeping it `pub` exposes an internal implementation detail. If `register_tools` is the only caller, the struct can either be made private or removed entirely in favour of a direct JSON literal.
- **Direction**: Replace `serde_json::to_value(NoArgs::new()).unwrap()` with `serde_json::json!({ "type": "object", "properties": {} })` directly in the `Tool::new(...)` calls, and delete `NoArgs`.

---

**Finding S5**
- **File**: `src/ollama_client/async_client.rs` line 5
- **Issue**: `BASE_URL` is hardcoded as a specific LAN IP address (`http://10.244.35.194:11434`). The `generate` function also creates a fresh `reqwest::Client::new()` on every call.
- **Why**: Hardcoded LAN IPs break whenever the server moves, the network changes, or the project runs on a different machine. `reqwest::Client` is designed to be created once and reused (it maintains a connection pool internally) — creating a new client per request wastes that pool. Both values should come from config or be held in `AppState`.
- **Direction**: Add `ollama_url: String` (or `base_url`) to `AppState` and pass it to the client functions. Create the `reqwest::Client` once in `AppState::new()` and store it there too.

---

**Finding S6**
- **File**: `src/handlers/ws_handler.rs` — overall structure
- **Issue**: `handle_socket` is doing at least four distinct things: frame routing, message parsing, running the agent loop, and streaming chunks to the client. It is currently ~90 lines and will grow further as more message types are added.
- **Why**: Long functions that mix concerns are hard to test, hard to reason about, and harder to extend without introducing bugs. In Rust specifically, deeply nested code (as this function already has) also tends to cause borrow checker issues since variables end up with wider scopes than they need. The agent loop alone — calling Ollama, parsing the stream, detecting tool calls, dispatching, re-entering — is a coherent unit that deserves its own function.
- **Direction**: Extract an `async fn run_agent_loop(conversation: &mut Conversation, state: &AppState, socket: &mut WebSocket, request_id: Option<String>) -> Result<(), ...>` function. `handle_socket` then becomes a thin frame-routing loop that delegates to it.
